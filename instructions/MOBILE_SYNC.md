# Синхронизация замеров КП и данных локомотивов

Эта памятка для разработчика мобильного приложения.  
Ниже описано, как сейчас устроен обмен данными между мобильным приложением и сервером RTPS, какие данные являются источником истины и как вести себя при конфликте записей.

## Главное правило

В системе есть два разных типа данных:

1. `referenceData` - справочник локомотивов и их колесных пар.
2. `archiveData` - архив замеров КП.

Справочник локомотивов и архив замеров синхронизируются отдельно.  
Не надо смешивать их в один объект и не надо пытаться обновлять архив через справочник.

## Авторизация

Сейчас все веб-модули используют общий cookie `rtps_session`, который подписывается общим секретом из:

```text
data/web_secret.txt
```

Что это значит для мобильного приложения:

1. Нельзя полагаться на старые отдельные логины модулей.
2. Если приложение обращается к HTTP API сервера, оно должно работать через текущую общую авторизацию RTPS.
3. Если в приложении используется офлайн-обмен через QR, файл или буфер обмена, то авторизация на сам payload не завязана, но сервер при импорте всё равно проверяет права пользователя.

Итог: для мобильного клиента ориентир один - общая авторизация RTPS, а не локальная авторизация конкретного модуля.

Если мобильное приложение получает `303`, это обычно означает не ошибку сервера, а редирект на страницу входа.  
Причина почти всегда одна из двух:

1. запрос идёт без валидного `rtps_session`;
2. запрос отправлен не на тот URL и попал на маршрут, который защищён авторизацией.

Что делать:

- сначала выполнить вход через `http://yrtps.ru/login`;
- сохранить cookie `rtps_session`;
- использовать этот cookie во всех запросах к API;
- если синхронизация идёт через WebView или встроенный браузер, не терять cookie между запросами.

## Что считается источником истины

### Для справочника локомотивов

Источник истины - данные справочника на сервере.

В справочнике хранятся:

- серия локомотива
- номер локомотива
- количество КП
- количество секций
- восьмизначный номер
- год выпуска
- срок службы
- номера и типы КП
- диаметры КП

### Для замеров КП

Источник истины - архив замеров.

Один замер должен храниться как цельная запись:

- дата замера
- локомотив
- вид ремонта
- колесные пары
- все параметры слева и справа

Частичное обновление одной строки допустимо, но на сервере замер всё равно хранится как единая сущность по ключу:

```text
date + locomotive + repair_type
```

## Форматы обмена

### 1. Справочник локомотивов

Экспортируется как `referenceData`.

Пример структуры:

```json
{
  "formatVersion": 2,
  "exportType": "referenceData",
  "exportedAt": "2026-06-28T12:00:00+03:00",
  "locomotives": [
    {
      "series": "ТЭМ2",
      "number": "7745",
      "wheelPairCount": 6,
      "wheelPairs": [
        {
          "number": 1,
          "axisNumber": 1,
          "diameterLeft": 1180,
          "diameterRight": 1181
        }
      ],
      "manufactureYear": "1984",
      "serviceLife": "25",
      "sortOrder": 10,
      "updatedAt": 1719560000000,
      "deletedAt": 0
    }
  ]
}
```

Что важно:

- `series` и `number` - ключ локомотива.
- `wheelPairCount` - ожидаемое число КП.
- `wheelPairs` - список КП локомотива.
- `diameterLeft` / `diameterRight` - текущие диаметры.
- `updatedAt` и `deletedAt` нужны для выбора актуальной версии.

### 2. Архив замеров

Экспортируется как `archiveData`.

Пример структуры:

```json
{
  "formatVersion": 1,
  "exportType": "archiveData",
  "exportedAt": "2026-06-28T12:00:00+03:00",
  "archive": [
    {
      "createdAt": "2026-06-28T12:00:00+03:00",
      "measurementId": "pc-2026-2026-06-28-7745-ТО3",
      "locomotive": {
        "series": "ТЭМ2",
        "number": "7745",
        "wheelPairCount": 6,
        "comment": "",
        "isNew": false
      },
      "repairType": "ТО3",
      "measurementDate": "2026-06-28",
      "wheelPairs": [
        {
          "number": 1,
          "left": {
            "flangeThickness": 27,
            "flangeWear": 0.5,
            "flangeSteepness": 6,
            "bandageThickness": 63,
            "bandageDiameter": 1180
          },
          "right": {
            "flangeThickness": 28,
            "flangeWear": 0.4,
            "flangeSteepness": 7,
            "bandageThickness": 64,
            "bandageDiameter": 1181
          }
        }
      ],
      "source": "pc"
    }
  ]
}
```

Что важно:

- Один элемент `archive` = один замер.
- `wheelPairs` хранит колёсные пары.
- Все параметры слева и справа идут внутри каждой пары.
- Поле `measurementId` желательно сохранять и использовать как стабильный идентификатор замера.

## Как импорт работает на сервере

### Импорт справочника

При импорте `referenceData` сервер:

1. Группирует локомотивы по `series + number`.
2. Оставляет самую актуальную запись.
3. Сравнивает версии по приоритету:
   - `updatedAt`
   - `deletedAt`
   - `sortOrder`
4. Обновляет локомотив и его КП.

Практическое правило для мобильного приложения:

- если локомотив изменился на телефоне, отправляй его целиком;
- не надо пытаться отправлять только одну КП, если менялась структура локомотива;
- после импорта сервер сам выберет более свежую версию.

### Импорт замера

При импорте `archiveData` сервер:

1. Берёт замер как цельную запись.
2. Находит существующий замер по комбинации:
   - дата
   - локомотив
   - вид ремонта
3. Удаляет старую версию этого замера.
4. Записывает новый замер целиком.

Практическое правило:

- если пользователь на телефоне исправил замер, нужно отправить весь замер целиком;
- сервер не сливает замеры по отдельным ячейкам;
- последний отправленный полный замер для этой даты и вида ремонта считается актуальным.

## Правила для мобильного приложения

### При первой синхронизации

1. Сначала получить справочник локомотивов.
2. Потом загрузить архив замеров.
3. Потом заполнить локальную базу приложения.

### При работе офлайн

1. Приложение может редактировать локальный кэш.
2. Все новые и изменённые замеры помечаются как ожидающие синхронизации.
3. При восстановлении связи сначала отправляется справочник, потом архив.

### При отправке на сервер

1. Сначала убедиться, что есть свежая авторизация.
2. Если менялся только справочник, отправить `referenceData`.
3. Если менялись замеры, отправить `archiveData`.
4. После успешной отправки обновить локальные флаги синхронизации.

## Конфликты

### Локомотивы

Если один и тот же локомотив изменён и на сервере, и на телефоне:

- ориентироваться на более свежую запись по `updatedAt`;
- если есть удаление, учитывать `deletedAt`;
- не затирать руками более свежую запись более старой.

### Замеры

Если один и тот же замер уже есть на сервере:

- замер по той же дате, локомотиву и виду ремонта заменяется целиком;
- частичный merge по отдельным полям не нужен;
- приложение должно присылать полную запись замера.

## Что должен уметь мобильный клиент

1. Показать список локомотивов из сервера.
2. Показать карточку локомотива с его КП.
3. Создавать и редактировать замеры КП.
4. Отправлять изменения справочника на сервер.
5. Отправлять изменения архива замеров на сервер.
6. Обновлять локальный кэш после успешной синхронизации.

## Что не надо делать

1. Не хранить отдельную “свою” правду для локомотивов, если сервер уже отдал свежую версию.
2. Не пытаться объединять разные замеры в один.
3. Не делать отдельную авторизацию для модулей, отличную от общей RTPS.
4. Не считать, что старый путь авторизации модулей ещё актуален.

## Коротко для разработчика

- `referenceData` - справочник локомотивов.
- `archiveData` - архив замеров КП.
- Справочник и архив синхронизируются отдельно.
- Замер отправляется целиком.
- Справочник обновляется по самой свежей версии.
- Авторизация теперь общая для RTPS, через `rtps_session`.
